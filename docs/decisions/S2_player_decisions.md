## D121 학습 없는 방법도 정식 선수 (D103 옆)

- 라우터 슬롯·다중 배관 슬롯에는 **학습 없는 방법 (예: 섹션 3) 최적화, 저장소 Navaljey/pipe-routing-opt)** 도 같은 규칙으로 제출할 수 있다.
- 조건은 학습 기반 방법(D103)과 같다: 슬롯 인터페이스 (D3·D49·D50 ⑧), 심판 불변 (D71), 결정적 예산 (D97 — 자기 예산을 정의해 제출), 판정 (D98·D99), 하드웨어 몫 (D122).
- 같은 평가셋·같은 머신 조건의 곡선에서 **D77 사전식으로 위에 있는 쪽을 채택**한다.
- **섞어도 된다** (예: 최적화의 다중 배관 조정 + V3 라우터). 섞은 제출물은 구성 요소와 각 요소의 출처(커밋)를 함께 적는다.
- 학습이 없는 방법은 "학습 시간 제외" 항목이 없을 뿐, 추론(실행) 시간은 모두 곡선에 들어간다 (D68).
- `docs/v3_contract.md` 에 이 결정을 넣는다 (V3 계약이 곧 선수 계약 — 제목·도입부에 "선수 = V3 (학습) 또는 학습 없는 방법" 을 명시).

## D122 하드웨어 몫 — 시나리오당 CPU 코어 예산 (시나리오 내부 병렬)

- **시나리오 하나에 쓸 수 있는 CPU 코어 = E1 측정 조건의 몫 = 2 코어** (E1 머신 4 코어 ÷ 동시 실행 2, D110 ①).
  - 그 안에서는 시나리오 내부 병렬을 자유롭게 허용한다 (작업자 2개 등).
  - 측정은 E1 조건 그대로 (같은 머신 사양, 동시 실행 2) 에서 한다. 한 시나리오가 2 코어를 넘게 쓰면 그 곡선은 판정에 쓰지 않는다.
- 근거: 판정은 벽시계 곡선 (D98) 이다. 하드웨어를 더 쓴 만큼 빨라진 것은 알고리즘 우위가 아니다. 이 몫이면 **E1 동결 기준선 곡선을 다시 재지 않고** 같은 조건으로 겨룬다 (기준선은 몫 2 코어 중 1 코어만 썼다 — 기준선 구현의 한계로 기록).
- 보고: 곡선과 함께 **시나리오별 CPU 시간 합**·사용 작업자 수·최대 동시 코어 수를 적는다.
- 결정성 (D72): 병렬 결과도 같은 입력·코드·시드면 같은 출력이어야 한다 (작업 분배 순서에 따라 결과가 바뀌지 않게).
- GPU 등 가속기 사용 몫은 아직 정하지 않는다 → **M34**. 그 전까지 가속기를 쓴 결과는 "가속기 사용" 으로 표시해 따로 보고한다 (채택 판단은 소유자).
- 섹션 3) 은 병렬 4 를 계획했다 (OPT.Dec10·Dec16) → 2 로 맞춘다. 이 결정 전의 병렬 결과는 참고로만 쓴다.

## 보완 — D120 구현 요구사항 추가 (섹션 3) 요청 ①②)

`docs/decisions/S2_preference_decisions.md` 구현 요구사항 1~7 에 더한다.

8. **실제 무게와 선호 벌점을 따로 보고.** 판정(D77)은 합친 J 로 한다. 출력·리포트에는 배관별·전체로 **J_physical (선호 제외: 직관·엘보·밸브·관통·서포트)** 과 **preference (선호 벌점)** 을 나눠 적는다. 벌점 크기를 잘못 정했을 때 원인을 찾기 위해서다.
9. **책임 배관 쌍 조회.** 금지 위반과 배관 쌍 선호 벌점마다 원인이 된 배관 쌍 (p, q) 와 구간을 알려 주는 조회 함수. 서포트 힌트 (D100) 와 같은 방식 — 조회 전용, 검증기 채점과 같은 함수, 결과 불변 시험. 출력 violations·preference 항목에도 쌍을 적는다.

## 보완 — D118 리듀서 완료 기준 추가 (섹션 3) 요청 ③)

- 배관 간 간섭 판정 (`multi.routes_conflict`) 과 증분 검증 (Session) 이 리듀서 배관의 **구간별 r** 을 쓰는지 확인하고, 시험을 건다 (두 구경 구간이 각각 다른 문턱으로 판정되는 사례). S2-3b 완료 기준에 넣는다.
